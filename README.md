# GOLDEN CITY — Visualization

מערכת פיתוח בעברית לניהול מתחמים, בדיקה גיאומטרית, תצוגת תלת־ממד ורינדור מקומי. זו המשך הגרסה הראשונית, עם אותם מזהי מבנים, תיקי פרויקטים ונתוני דוגמה.

המשך הפיתוח נמצא בענף `development/architectural-v3`. בסיס v2 נשמר תחת `outputs/v2/`; תוצרי הניסוי החדשים נמצאים תחת `outputs/v3/`. כל ההדמיות שבמאגר הן סינתטיות. קוד קליטת המקורות אינו מהווה אישור למיקום או לדיוק באתר אמיתי.

## הפעלה

כלים שנבדקו בסביבה זו: Python 3.12, Node 24, Blender 4.3.2, Chromium 154. Three.js 0.180.0 מופץ מקומית ברישיון MIT; אין תלות ב־CDN. Blender מרנדר באמצעות Cycles על CPU. מנוע הסרת הרעש האופציונלי אינו זמין בבניית Blender הזו, ולכן אינו מופעל.

```sh
cd /workspace/golden-city-visualization
python -m venv .venv
.venv/bin/python -m pip install --no-cache-dir -r requirements-dev.txt
npm ci --cache /tmp/golden-npm-cache --ignore-scripts --no-audit --no-fund
npm run vendor
blender --version
.venv/bin/python app.py
```

השרת מאזין בפורט 8000. ניתן לשנות באמצעות `PORT`. השתמשו בממשק השירות של סביבת האירוח. השירות מיועד לפיתוח פרטי; אין בו מערכת חשבונות. תיקי המשתמשת, מקורות שהועלו והרינדורים נשמרים ב־`data/`, ואינם נכנסים ל־Git. תהליך השרת צריך לעלות מחדש לאחר שחזור הסביבה.

## שימוש בממשק

1. פתחו את הדוגמה הסינתטית או העלו קובץ פרויקט.
2. בדקו את גבול המתחם ואת דוח החריגות, ואז אשרו את ההעמדה. האישור אינו אימות מול קדסטר.
3. בתצוגת התלת־ממד גררו לסיבוב מצלמה, השתמשו בגלילה לזום ובחרו מבט אווירי או רחוב. שמרו מצלמה בשם כדי להשתמש שוב באותה נקודת מבט.
4. בחרו מבנה באמצעות הרשימה או המודל. ערכו צבע, חומר חזית או מרפסת. גוף המבנה והמבנים האחרים נשמרים. הוספת מרפסת היא שינוי גיאומטרי מפורש במבנה הנבחר.
5. הפיקו תמונה באמצעות Blender. הרינדור עשוי להימשך עשרות שניות; התמונה, המצלמה, קובץ הסצנה ו־`.blend` נשמרים.
6. שחזרו גרסה כדי לחזור למבנים, למצלמות ולמקורות הקודמים. השחזור יוצר גרסה חדשה ומשאיר את ההיסטוריה.
7. ניתוח מרפסת מציג היטל במבט על וחתך של הבליטות הידועות. כשמידע על עצמים מעל המרפסת אינו שלם, שטח פתוח לשמים נשאר לא ידוע. אין אישור כשרות או אישור הנדסי.

פתיחת תיק חדש לפי כתובת וגוש יוצרת תיק ללא גבולות או מבנים. קליטת קובץ מקור מוסיפה תוצאות פענוח וחתימה לתיק, ואינה ממציאה ממנו תוכנית העמדה. הממשק מציג את הנתונים החסרים. רינדור של אתר אמיתי דרך השרת חסום עד להשלמת מנוע טופוגרפיה וסביבה מדודות, גם אם נרשמו סקירות אנושיות.

## נתונים וקואורדינטות

קובץ פרויקט כולל `name`, `crs` מטרית מישורית, `boundary` מסוג GeoJSON Polygon ו־`buildings` מערך של Features. לכל מבנה `properties.id` קבוע, `height` במטרים ו־`floors` שלם חיובי. `color` הוא hex ו־`material` אחד מ־`stone`, `plaster`, `brick`, `glass`. אופציונלית `base_elevation` הוא גובה מקומי במטרים. פוליגוני המבנים ללא חורים. כל הקואורדינטות הן XY בלבד וכולן באותה מערכת; הגובה נפרד.

מרפסות הן `properties.balconies`: רשומות עם `id`, `footprint` מסוג Polygon בקואורדינטות הפרויקט, `elevation` שהוא פני הלוח העליונים במטרים, `thickness` (ברירת מחדל 0.25) ו־`railing_height`. `properties.slabs` ו־`overhead_obstructions` בפרויקט מאפשרים לתאר לוחות או קירויים נוספים עם footprint, elevation ו־thickness. רק גיאומטריה שסופקה נבדקת.

בלנדר, Three.js ויצוא OBJ החדש משתמשים ב־XYZ מקומי עם Z כלפי מעלה; מקור XY הוא מרכז השטח של הגבול. יצוא OBJ מהאבטיפוס הקודם השתמש ב־Y כלפי מעלה: יש להמיר אותו לפני טעינתו כמקור בתצוגה החדשה. הקובץ הישן נשמר כדוגמה היסטורית.

### גבולות גיאוגרפיים והתאמת תוכנית

`POST /api/boundary` מקבל `{id,geojson,source_crs,source}`. מקור נתונים מתועד ב־`source` עם provider, reference, acquired_at בתאריך ISO ו־source_type. `EPSG:4326` נקרא בסדר אורך/רוחב. PROJ ממיר למערכת הפרויקט, ונבדק תחום השימוש של המערכת. גבול המקור נשמר בנפרד, ושינוי גבול מבטל אישור העמדה.

`POST /api/align` מקבל `{id,buildings,control_points,max_residual}`. נקודות ייחוס: `{plan_xy:[x,y],target_xy:[easting,northing]}`. נדרשים לפחות שלושה זוגות שאינם על קו אחד. ההתאמה מחשבת קנה מידה, סיבוב והזזה בלבד, ללא עיוות או שיקוף. שגיאה מעל הסף (ברירת מחדל 0.25 מ׳) דוחה את ההתאמה. נתוני המקור ושאריות ההתאמה נשמרים. זו התאמה מתמטית לפי הנתונים שסופקו; היא אינה מאמתת את נכונות נקודות הייחוס או גובה הקרקע.

### מקורות צילומיים ומודלים

קליטת PNG/JPEG ו־OBJ נבדקת בפועל. הקובץ המקורי נשמר ללא שינוי עם SHA-256. תמונה יכולה לקבל bounds מטריים להצבה במישור המפה; ללא bounds היא מקור לעיון. OBJ נטען בקואורדינטות XYZ מקומיות עם Z למעלה. שכבות המקור מוצגות ב־Three.js; בשלב זה הן אינן נכללות בתמונות שמפיק Blender. אין כאן פתרון אוטומטי של פוטוגרמטריה, כיול צילום או החלפת מבנים בתוך צילום. המקורות נשמרים כהכנה לפיתוח עתידי ואינם נחתכים או נכתבים מחדש בעקבות עריכת מבנה.

## בדיקות ותוצרים

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python scripts/test_report.py
.venv/bin/python render_acceptance.py

```

`examples/renders/` מכיל תמונות אמיתיות של רינדור Cycles: aerial.png, street.png, edited-aerial.png, comparison.png. הדוגמה שומרת את טביעת המבנה A המקורית ומוסיפה B ו־C סינתטיים להוכחת עריכה נקודתית. acceptance-report.json כולל חתימות אובייקטים, מסכות נראות ומצלמה זהה לפני/אחרי. שינוי מבנה יכול לשנות צללים ותאורה על עצמים אחרים גם כשגיאומטרייתם וחומריהם נשמרים בדיוק.

תפאורת כביש ורחבות נוספת מופעלת רק בפרויקט שסומן במפורש `synthetic:true`. פרויקט אמיתי אינו מקבל כבישים משוערים. גם אז מישור הקרקע ברינדור הוא סכמטי, ללא גובה מדוד.

## מה עדיין חסר

אין אימות אוטומטי של סמכות מקור GIS, קליטת DWG מורשית, KML/Shapefile/GeoPackage, פענוח אדריכלי אוטומטי של תוכניות סרוקות, טופוגרפיה מדודה, כיול מצלמה מתוך צילום, החלפת מבנים בתצלום תוך שימור הסביבה, או אישור מרפסות סוכה. קליטת PDF ו־DXF מחלצת רק את התוכן שהבודקים תומכים בו; היא אינה מסיקה מיקום, קומות או גובה. רשימת הפורמטים ב־`/api/capabilities` מבדילה בין חילוץ שנבדק בפועל לבין יכולת שטרם אומתה. אין הצהרה שהרינדור כבר ברמת הדמיה שיווקית מקצועית.

לכל ניסוי אמיתי נדרשים גבולות מוסמכים ותוכנית העמדה עם מערכת קואורדינטות, גבהים, מערכת גובה ונקודות בקרה. כתובת, גוש וחלקות לבדם אינם מספיקים לקביעת מיקום. חומרי תכנון ומחקר של אתרים אמיתיים אינם כלולים במאגר הציבורי.

## תיק מקורות, סקירות ומרפסות לפי מדיניות פרויקט

`POST /api/dossier` מקבל `{name,address,block,parcels}` ויוצר תיק נפרד ללא גיאומטריה. `POST /api/intake` מקבל `{id,name,content_base64}` ושומר את הקובץ המקורי עם חתימה ותוצאת חילוץ; הכתובת אינה משויכת אוטומטית לגיאומטריה. `POST /api/readiness` מציג השלמות ומגבלות מנוע. נתוני משתמש, הצעות עיצוב וניסוי סינתטי מסומנים בנפרד.

`POST /api/review` רושם סקירה אנושית הקשורה לחתימת מקור, לחתימת הגיאומטריה הנוכחית, לפרויקט, לתאריך ולשם סוקר. המקור והגיאומטריה נפתחים ונבדקים שוב. שינוי פיזי מבטל את התאמת הסקירה לגרסה; שינוי צבע או מצלמה שומר את אותה גיאומטריה. המערכת אינה מאמתת את סמכות הסוקר ואינה נותנת אישור קדסטרי או מקצועי.

`POST /api/sukkah-screen` מקבל `{id,building_id,balcony_id,policy,details,overhead_complete}`. המדיניות צריכה לכלול דרישות מידות עם מקור, גורם מוסמך וגרסה. הנתונים כוללים שטח סוכה מלבני מפורש, גובה פנוי, מערכת גובה, מקור מדידה ותיעוד דפנות וסכך. היטל וחתך נשענים על הגיאומטריה הקיימת בלבד. תוצאה חיובית היא מועמד לבדיקה מקצועית; `halachic_approval` נשאר false גם אם צורפה הצהרת אישור שלא אומתה.

## מסירה מאומתת — חובה לכל פרויקט

לפני יצירת קישור או הורדה, `delivery_validation.validate_file` פותח מחדש את התוצר ומחזיר ראיות בדיקה. `delivery_guard.verify_for_delivery` הוא שער המסירה המשותף לשרת: קובץ חסר, ריק, פגום, גדול מדי או שונה מהחתימה הצפויה נחסם. מטמון הבדיקות קשור לתוכן ולתפקיד הקובץ; מסמך HTML וקישוריו נבדקים מחדש. השרת שולח את אותם בייטים שנבדקו, עם חתימת SHA-256. הורדת OBJ ודוח הפרויקט בממשק עוברת דרך השער, ולא דרך יצירת קובץ לא בדוק בדפדפן.

- PNG/JPEG: בדיקת המבנה, פתיחה חוזרת ופענוח כל הפיקסלים באמצעות Pillow, ממדים וגבולות גודל, שונות חזותית, ופענוח נוסף באמצעות FFmpeg. תמונת רינדור אחידה וריקה נחסמת. תמונת מקור שהמשתמשת העלתה יכולה להיות אחידה; הדוח מסמן אותה במפורש כלא אינפורמטיבית ולא כרינדור שעבר.
- OBJ/GLB/BLEND: ייבוא חוזר בתהליך Blender חדש, ללא הפעלה אוטומטית של סקריפטים. נבדקים קודקודים, פאות, שטח גיאומטרי בעולם, אובייקטים וגאומטריה סופית. כאשר יש נתוני מקור, מושווים גם גבולות כל אובייקט, ספירות ומיקום/כיוון/זווית מצלמה. OBJ אינו מכיל מצלמות. OBJ חדש מצהיר על XYZ מקומי עם Z למעלה; GLB משתמש בהמרת הצירים התקנית של glTF.
- PDF: ספירת עמודים באמצעות pdfinfo, רינדור כל העמודים באמצעות pdftoppm, ופתיחה ופענוח של תמונות העמודים. אין כרגע יצוא PDF של המערכת; מנגנון הבדיקה נבדק עם מסמכי PDF אמיתיים שנוצרו לצורך הבדיקות.
- HTML: כל תמונה משובצת מפוענחת, כל יעד מקומי קיים ונפתח מחדש, ויעד חיצוני מסומן כלא מאומת. מסמכי HTML עם מעגל קישורים נדחים במנגנון הנוכחי.
- ZIP: CRC, רשימת קבצים מלאה וחתימות ב־manifest.json, חילוץ לתיקייה זמנית, ופענוח/ייבוא מחדש של כל קובץ שחולץ. כל עותק סופי נקרא שוב אחרי האריזה ומושווה לבייטים שנבדקו. קבצים בפורמט ללא בודק נתמך אינם נמסרים אוטומטית.

הראיות נפרדות מנגישות המשתמשת: `user_accessibility=not_verified` נשמר עד שיש אישור אמיתי של נגישות ההורדה אצל המקבלת. תגובה תקינה מהשרת או פתיחת תמונה ב־Chromium בסביבה אינם מוכיחים שקישור בצ׳אט של Codex נפתח אצל המשתמשת.

```sh
# הפקה חוזרת של שלוש התמונות וייצוא מודלים עם בדיקות עצמאיות:
.venv/bin/python render_acceptance.py
# יצירת Contact Sheet, גלריה עצמאית, חבילה ובדיקות אחרי חילוץ:
.venv/bin/python delivery.py --output deliverables --include-blend
# כל בדיקות המערכת כולל מנגנון המסירה:
.venv/bin/python scripts/test_report.py
```

החבילה כוללת `golden-city-gallery.html` המכיל את התמונות בתוכו, `contact-sheet.png`, שלוש תמונות הרינדור, השוואה, מודלים ודוחות. פתחו את הגלריה בדפדפן או חלצו את ZIP ופתחו את תמונות PNG. בממשק יש אזור ״תוצרי הניסוי — צפייה והורדה״; השרת מאמת כל תוצר לפני החזרתו. הבדיקות בסביבת הדפדפן המנוהלת פותחות את בייטי HTML ומפענחות את התמונות, אבל מדיניות הדפדפן חוסמת ניווט `file://`. לכן פתיחת קובץ מקומי אצל המשתמשת ונגישות קישורי ההורדה אינן מוצגות כנבדקות.

תלויות נוספות לבדיקת מסירה: Blender, FFmpeg, Chromium, pdfinfo ו־pdftoppm. אין להחליף בדיקה חסרה בתוצאה עוברת; יש לעצור את מסירת אותו תוצר ולהציג את הסיבה.

## צפייה עצמאית בתמונות ובמודל הקיים

`deliverables/golden-city-viewer.html` הוא קובץ עצמאי המכיל את שלוש תמונות הרינדור המקוריות ואת מודלי GLB הקיימים לפני ואחרי עריכת מבנה A. לאחר שהקובץ נמסר והורד, פתחו אותו באמצעות Chrome או Edge עדכני. יש להוריד את קובץ HTML עצמו; תצוגת הקוד שלו ב־GitHub אינה מפעילה את המודל. התמונות מוצגות בראש הדף, ותחתיהן מופיע המודל: גרירת עכבר מסובבת מצלמה, גלגלת מקרבת, והכפתורים בוחרים מבט אווירי, מבט רחוב או את הגרסה הקיימת לאחר העריכה. ניתן לשמור כל PNG ואת GLB המוצג בנפרד. אין צורך בשרת או בחיבור לרשת לצפייה בקובץ שהורד; נדרשת תמיכת WebGL לתלת־ממד.

האריזה משתמשת בקובצי המקור שכבר נבדקו ומשבצת את Three.js ואת רישיון MIT שלו. היא אינה מפיקה מודלים או תמונות מחדש. הגיאומטריה, החומרים, מיקומי האובייקטים והמצלמות נשמרים; עוצמת התאורה בתצוגת הדפדפן מותאמת להצגה. תמונות PNG, מודלי המקור וחבילת ZIP הקיימת נשארים זהים בבייטים.

```sh
# אריזה של התוצרים הקיימים לקובץ צפייה עצמאי:
.venv/bin/python scripts/build_offline_viewer.py
# בדיקה עצמאית מחייבת אחרי האריזה ולפני מסירה:
.venv/bin/python scripts/test_offline_viewer.py
```

בנוסף לשער בדיקת HTML המשותף, בדיקת הדפדפן פותחת מחדש את הקובץ, מפענחת את התמונות, מייבאת את GLB המשובצים, משווה מזהים, ספירות קודקודים ומשולשים, גבולות ומצלמות, בודקת סיבוב ומבטים, ומורידה מחדש קבצים להשוואת בייטים. היא חוסמת בקשות רשת ובודקת שגם מקור התוצרים ו־ZIP לא השתנו. דוח הבדיקה וצילומי התצוגה נשמרים כברירת מחדל תחת `/tmp/golden-offline-viewer/`; יש לפתוח ולבדוק את צילומי התלת־ממד חזותית לפני המסירה.

הבדיקה בוצעה ב־Chromium באמצעות קריאה חוזרת של HTML והפעלתו ב־`about:blank`, עם רשת כבויה. ניווט `file://` בסביבה המנוהלת ופתיחה בלחיצה כפולה במחשב המשתמשת לא אומתו. גם נגישות הקובץ אצל המקבלת אינה מאומתת: קובץ תקין בסביבה אינו הוכחה למסירה מוצלחת. אין להציג נתיב פנימי או קישור שלא נפתח אצל המקבלת כמסירה שהושלמה.
